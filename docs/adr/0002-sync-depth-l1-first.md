# ADR-0002：跨端同步先做 L1（IMAP 原生），L2 抽象在 P0 预留

- **状态**：已接受
- **日期**：2026-10-18
- **决策者**：xyyi0719

---

## 背景

需求原文是"**可以同步所有账号信息的**"。这句话有歧义，直接按字面实现会做出错误的承诺，
因为邮件协议本身能覆盖的同步范围比直觉小得多。

把"账号信息"拆成三层：

| 层 | 内容 | IMAP 能否承载 | 跨端机制 |
|---|---|---|---|
| **L1** | 邮件本体、文件夹、**已读/未读**、**星标**、**移动**、**删除**、服务器标签 | ✅ **能**——IMAP flag 本来就是服务器权威状态 | IMAP 原生，**零服务器** |
| **L2** | 本地标签、过滤规则、签名、模板、联系人、阅读进度、偏好设置 | ❌ 不能 | 需自建同步服务（或退化为单机） |
| **L3** | 授权码 / 密码 / OAuth refresh token | ❌ 不能 | 需自建服务（存密文），或每设备各配一次 |

关键洞察：**L1 是 IMAP 免费送的**。只要把 flag 写回服务器，"手机标已读，PC 上也是已读"
就自动成立，不需要任何自建服务器、不需要用户注册账号、不需要处理数据合规。
这恰恰是"多端邮件客户端"最核心、也是用户最能感知的同步体验。

L2/L3 则需要额外引入一个"Xremail 同步服务"（Rust/axum），带来：运维负担、
账号体系、可用性依赖、隐私合规、用户教育成本。

---

## 决策

**先做 L1，L2/L3 在 v1.0 降级为"每设备独立"，但在 P0 就把抽象接口与 schema 预留好。**

具体：

1. **P0** 落地 `xremail-api` 中的预留 trait：
   - `SyncBackend` —— 远端同步后端接口（自建服务实现它）
   - `VaultStore` —— 加密凭据库接口
   - 配套 schema：`local_secret` / `label` / `rule` 表
2. **P1–P5** 只实现 L1：所有状态变更写回 IMAP 服务器。
3. **P6**（可选）实现自建 E2EE 同步服务，让 L2/L3 跨端。
4. **UI 必须如实说明**哪些会同步、哪些不会——不得暗示"所有设置都会同步"。

---

## 理由

- **先拿到 80% 的价值**：L1 覆盖了用户日常最在意的"多端一致"。
- **零运维依赖**：MVP 不需要服务器、不需要账号体系、不需要处理服务端不可用。
- **不返工**：P0 预留 trait 后，P6 只是"新增一个实现"，核心业务代码零改动。
- **隐私更好**：邮件正文与 flag 全程不经过我们的服务器（除非用户主动启用 L2 同步）。
- **风险可控**：P6 是可选项，做不出来也不影响 v1.0 成立。

---

## 后果

### 正面

- v1.0 无服务端依赖，可直接发布桌面版与 Android 版。
- 隐私叙事更强："邮件内容与阅读状态永远不经过第三方服务器"。
- 架构上把"同步"抽象成 trait，未来接 JMAP / Exchange 也不影响 L2 的实现。

### 负面 / 代价

- **v1.0 的规则/签名/标签不跨端** → 用户在 PC 配的签名，手机上要用一次。必须明确告知。
- **需要写"自建同步服务"这个组件**（P6，约 2~3 周），并要处理：
  - 端到端加密（服务端零知识）
  - 主密码管理与恢复（**丢了主密码 = 丢了同步数据**，UX 必须做足）
  - 冲突合并（字段级 LWW + HLC）
  - 部署与升级（Docker Compose / 一键脚本）
- **L3 凭据跨端是敏感决策**：即使加密，也要让用户理解"信任我的服务器"这件事。
  → 因此 P6 的凭据同步做成**默认关闭、显式开启**。

### 风险与缓解

| 风险 | 缓解 |
|---|---|
| 用户以为"所有东西都同步"，产生预期落差 | UI 在设置页用清单明确列出"会同步 / 不同步"，并加说明链接 |
| P6 一直没做，架构预留变成死代码 | P0 的 trait 必须有**真实可运行的 mock 实现**并被测试覆盖，否则视为未完成 |
| 主密码丢失导致数据永久丢失 | 恢复码机制 + 明确警告 + 提供"重置同步数据"入口 |
| E2EE 实现有误 | 用标准库（argon2 + XChaCha20-Poly1305）+ 测试向量 + 第三方审计 |

---

## 备选方案

### A. 一上来就做完整自建同步服务（L1+L2+L3 全跨端）

- **优点**：功能最完整，差异化最强。
- **否决理由**：把"同步服务"这个独立子项目放在协议层之前做，风险与收益倒挂。
  用户还没收到第一封邮件，先要装服务器。**先验证核心价值再扩展。**

### B. 只做 L1，永不预留 L2

- **优点**：最省事。
- **否决理由**：后期加 L2 需要改动 `xremail-store` schema 与多处调用点，
  反而是**更大**的返工。P0 预留成本极低（几个 trait + 几张表）。

### C. 用 CardDAV / Google Contacts 承载 L2

- **优点**：复用现成标准。
- **否决理由**：只覆盖联系人，覆盖不了规则/标签/签名/偏好。
  可作为 P5 的**补充**（联系人同步），不能替代同步服务。

---

## 复审条件

- 用户调研显示"规则/签名跨端"是**首要**需求而非"邮件状态跨端" → 提前 P6。
- 决定做"家庭/团队共享"版本 → L2 必须成为一等公民，需要重新设计多用户模型。
- 决定把 Xremail 做成商业产品并以"同步服务"为卖点 → P6 从可选变为必做，
  且需要补账号体系、计费、可用性 SLA。
